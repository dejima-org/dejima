# Working on dejima

Notes for an agent working **on this repo**. None of this is dejima's own
behaviour — nothing here describes what dejima does for the projects it
sandboxes. For that, see `hooks/sandbox-context.sh` (what a sandboxed agent is
told) and `README.md`.

## The test suite is split, and a sandbox can only run half of it

`test/runtime.bats` builds the image and boots real containers, so it needs a
working Docker. A dejima sandbox does not have one — the container has no Docker
socket, by design. Everything else runs anywhere:

```sh
bats test/static.bats test/project.bats test/remote.bats \
     test/audit.bats test/proxy.bats test/config.bats
```

**CI runs `test/runtime.bats` on every pull request**, as a separate `runtime`
job in `.gitea/workflows/tests.yml`. So being unable to run it locally is not a
reason to stop, to hedge, or to leave a change unfinished. Run the fast suite,
open the PR, and say plainly in the PR body that the runtime half was not run
locally.

**But do not read "CI covers it" as "it passed."** That job is pinned to
`runs-on: dejima-runtime`, a label only the one configured self-hosted runner
carries — it needs the host network namespace, the Docker socket, and a shared
volume, none of which a workflow can request. If that runner is offline the job
**queues instead of failing**, and the PR sits with the runtime half neither
green nor red. Check the PR's actual checks before treating it as verified, and
if the job is still queued, say so rather than implying it ran.

If a change touches what gets mounted, whether the firewall runs, or which
credentials cross the container boundary, that runtime run is the only thing
exercising it end to end. Worth asking the operator to run it on the host rather
than waiting on the runner.

## One fast-suite test also fails inside dejima, for the same kind of reason

`test/proxy.bats`'s "forwarder tls mode refuses to start without a cert" spawns
`docker/anthropic-proxy-forwarder.js` in `tls` mode, which binds
`127.0.0.1:443`. When the session is itself running with
`[credentials] transport = tls` — the default — the container's own forwarder
already holds that port, so the test's forwarder dies with `EADDRINUSE` before
it reaches the assertion it is actually making.

It passes in CI, where nothing else is on 443. Inside dejima it fails, and the
failure says nothing about the code under test. Check for it before assuming a
change of yours broke it:

```sh
ss -tlnp | grep ':443'
```

A listener owned by `anthropic-proxy-forwarder.js` means this is the collision,
not your change.

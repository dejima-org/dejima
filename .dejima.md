# Working on dejima

Notes for an agent working **on this repo**. None of this is dejima's own
behaviour — nothing here describes what dejima does for the projects it
sandboxes. For that, see `hooks/sandbox-context.sh` (what a sandboxed agent is
told) and `README.md`.

## The test suite is split, and a sandbox can only run half of it

`test/runtime.bats` builds the image and boots real containers, so it needs a
working Docker. A dejima sandbox does not have one — the container has no Docker
socket, by design. Everything else runs anywhere, which is what the CI job names
mean: `confined` for the suites that need only a shell, `privileged` for the one
that does not.

## `bats` is a declared dependency here, not part of the image

It is in `.dejima/dependencies`, like any other project's test runner, rather
than baked into the base image for every project that never runs bats. So on a
sandbox whose image predates that approval, `bats` is simply absent — the fix
is the ordinary one the briefing describes (`dejima-project approve`, then
relaunch so the derived image is rebuilt), not installing it in-session.

If it is missing and you cannot get a rebuild, say the suites were not run
rather than reporting a change as tested.

**`parallel` is declared for the same reason**, because CI runs every suite
with `--jobs $(nproc) --no-parallelize-across-files` and `bats --jobs` needs
GNU parallel to do it. Without it bats exits with `Cannot execute N jobs
without GNU parallel` and prints no test output at all.

That failure is quiet in the worst way, so **check the exit status, not the
output**. A suite that never ran emits no `not ok` line, so the obvious
`| grep '^not ok'` check reports it as passing — which is how a change here
was once reported green against a suite that had not executed. Requiring both
a zero exit status and a non-zero count of `ok` lines catches it:

```sh
out="$(bats --jobs "$(nproc)" --no-parallelize-across-files test/config.bats 2>&1)"
rc=$?
n="$(grep -cE '^ok ' <<< "$out")"
[ "$rc" -eq 0 ] && [ "$n" -gt 0 ] || { echo "$out"; exit 1; }
```

## Two lanes: one for iterating, one for the pull request

Between edits:

```sh
bash test/run-confined.sh --changed
```

It reads `git diff` — committed, uncommitted and untracked — maps each path to
the suites that cover it, and runs only those. `--list` prints the selection
without running anything, and a path given as an argument stands in for one git
would have reported, so `--changed --list docker/Dockerfile` answers "what would
this change run?" directly.

Before opening a pull request, and for any claim that a change is tested:

```sh
bash test/run-confined.sh
```

That is the gate: every confined suite, no selection. Each run prints which lane
it was, and `--changed` says in as many words that it is not the gate. **A green
`--changed` run is not a tested change** — it is evidence about the suites it
names and nothing about the ones it skipped.

The map lives in `suites_for()` in `test/run-confined.sh` rather than in a table
here, so that it runs instead of being remembered, and so an agent cannot map a
change to the wrong suite by hand. A path matching no rule selects every suite:
a path nobody has mapped is a path nobody has decided about. When you add a
file that a specific suite covers, add the rule — `static.bats` checks the map
names only suites that exist, but nothing can tell that a rule is too narrow.

Both lanes run the tests within each file concurrently as well as the files
themselves, which is most of where the wall clock went. It is bats' own
`--jobs`, and it needs `flock` rather than GNU parallel; without `flock` the
script falls back to one at a time and says so.

**The concurrency is budgeted for the whole run, not per suite.** Every
selected suite runs at once, so what lands on the machine is suites × jobs;
asking each for `nproc` made that ten times the cores on a ten-core box. The
script targets roughly twice the cores in total and divides, and prints both
numbers. That is #295: several tests wait on a bounded deadline — a pty
reaching raw mode, a shipper polling, an audit finishing — and a saturated
machine blows through it, so they failed for the load rather than for the
thing they check. If you add a test that waits for something, assume the
machine is busy.

Each run reports what every suite ran as well as what failed, because a suite
that cannot start — a syntax error, or duplicate test names, which bats refuses
outright — exits nonzero having run nothing, and that reads as "no failures" to
anything counting only failures.

**CI runs `test/runtime.bats` on every pull request**, as a separate
`privileged` job in `.gitea/workflows/tests.yml`. So being unable to run it
locally is not a reason to stop, to hedge, or to leave a change unfinished. Run
the confined suites, open the PR, and say plainly in the PR body that the
privileged half was not run locally.

**Green means it ran.** The forge does not show a check green until every job
in it has finished and passed, and `runtime.bats` is one of those jobs — so a
green PR is one where the privileged half executed. There is no state in which
the checks are green and that suite was skipped.

What a queued run looks like is yellow or grey, not green. That job is pinned
to `runs-on: dejima-privileged`, a label only the one configured self-hosted
runner carries — it needs the host network namespace, the Docker socket and a
shared volume, none of which a workflow can request — so if that runner is
offline the job **queues instead of failing**, and the PR sits unfinished
rather than passing.

So: read the colour, and say what it says. Green is verified end to end and
should be reported that way. Yellow or grey is a run that has not happened yet,
and reporting it as passing is the thing to avoid. Hedging a green one is the
opposite error and is the more common one here — it reads as doubt about a
result that is not in doubt.

If a change touches what gets mounted, whether the firewall runs, or which
credentials cross the container boundary, that runtime run is the only thing
exercising it end to end. Worth asking the operator to run it on the host rather
than waiting on the runner.

## Pushing a branch here runs your code outside the sandbox

The moment you push, CI checks that commit out on a host and executes it — and
because the workflow runs `bats test/<suite>.bats`, every file in `test/` is
code that runs there, not just the workflow file. Nothing about that is under
the sandbox's firewall, and no one reads the diff first.

Practically: a helper you add to a test file gets executed on a machine outside
this container. Write test code you would be comfortable running there, and if
a change would have CI reach a new host, that belongs in
`.dejima/allowed-domains` in the same pull request — on this project the CI
allowlist is read from `main`, so an undeclared destination fails rather than
connects. See [docs/ci.md](docs/ci.md).

## Batch your pushes, because runs queue rather than supersede

Every push to an open pull request starts a full workflow run, and Gitea does
not implement `concurrency:` (see the comment at the top of
`.gitea/workflows/tests.yml`, which records the test). A second push does not
cancel the first: it queues behind it. So four pushes in ten minutes is four
full runs, and the load keeps arriving long after you have stopped pushing,
because the backlog is still draining.

That is not hypothetical here. A session pushing commit-by-commit while
iterating on a pull request queued enough runs to saturate this project's
forge: nginx stopped being able to open connections to Gitea at all, and the
requests that timed out were the runners' own `UpdateLog` and `UpdateTask`
calls plus the operator's browser. The forge went down for several minutes and
tripped uptime alerts.

So: **finish a change, then push once.** Commit as often as you like locally;
that costs nothing. What costs something is every `git push`. If you have three
commits to make, make them and push at the end, rather than pushing after each.

The same applies to forge API reads. `gitea-pr comments` fetches one request
per review on the pull request, so on a heavily reviewed one that is dozens of
requests per invocation. Run it when you need the answer, not repeatedly while
iterating, and never in a loop.

If a push does supersede a run you no longer care about, cancel the stale one
by hand in the web UI. Nothing does it for you.

## A test that reads its environment will pass here and fail on your machine

Twice now a test has stated a precondition by leaving something unset, which
only holds where nothing else set it. Both passed in CI and failed exactly where
the code was being worked on:

- `proxy.bats`'s cert check meant "no cert configured" by not setting
  `SANDBOX_CREDENTIAL_TLS_CERT` — but `entrypoint.sh` exports it into every
  tls-transport session, so inside a sandbox the guard under test never fired.
- `remote.bats`'s default-port check asserted on 7681, which is the port a real
  `dejima-ttyd` front door holds, so it failed on any host running the feature.

Both are fixed by stating the precondition (`env -u`, a stubbed `ss`) rather
than assuming it. When a test fails only in one environment, suspect this before
suspecting the code — and when writing one, set what you depend on.

## What lands on `main` here is a trust anchor, not just a release

`docs/responsible-use.md` is this project's own policy, and two of its points
bind while you are working *on* dejima rather than merely with it.

**`.dejima/allowed-domains` is read from `origin/main` by
dejima-ci-hardener**, which treats whatever it finds there as already
reviewed - that is how a CI runner decides what a job may reach. Adding a
domain to that file is not a convenience for one branch; it widens what every
future CI job on that runner can talk to, from the moment it merges. Say what
a domain is for in the pull request, and expect the question.

**Security here is not a later pass.** This repository's product is an
argument that a boundary holds. A change that quietly weakens one - a mount
that widens, a check that moves after the thing it guards, a test that stops
asserting what its name claims - is a defect in the product, not a rough edge
to tidy up afterwards. If you notice one while doing something else, say so
rather than leaving it for a pass that may not come.

## Write the comment that prevents the bug, not the one that shows your work

The prose here gets a compression pass periodically, and the same things get
cut every time. Save that pass the work:

- **Keep** the issue number, the failure mode, and why a check is shaped the
  way it is - stated as a property of the code that is there. Someone has to
  be able to not reintroduce the bug.
- **Cut how you found it.** Which CI run failed, how many attempts it took,
  what you suspected first: that is your story, not the reader's.
- **Cut what the code replaced.** "This used to live in X." "The old version
  did Y, which was worse because Z." Git holds that, and a reader debugging
  this line has no use for it.

  Its own bullet because it does not feel like padding - it feels like the
  reason. A previous shape is the easiest answer to "why is it shaped this
  way", so the rule above invites it if you are not watching. It is not an
  answer: if the reason only makes sense next to something that is gone, it
  has not been written yet. Say what is true of the code now and let the
  reason stand on that.

  The exception is code whose only purpose *is* the past - a cleanup for a
  rename, a compatibility shim, a migration. There the history is why the
  code exists at all, and cutting it leaves a block that reads as dead
  weight for the next person to delete.
- **Cut the second and third consequence.** State the first. A reader who
  needs the chain can follow it.
- **Cut anything the code directly below already says.**
- **Cut meta-commentary** - "the useful way to read this is", "what follows
  is why". Say the thing instead.
- **No numbers that drift.** Test counts, directory sizes, how many files a
  sweep found: wrong within a month, and nothing checks them. This applies to
  pull request descriptions too, which are read once and then stop being
  true.
- **One place.** An edge case belongs in `docs/`, not also in the README -
  the README is what someone needs on first contact.

This is not an argument for thinner documentation: the note on voice in the
README prefers thorough over polished, deliberately. It is an argument
against padding. A paragraph carrying one fact should be one sentence.

The blocks that survive every pass are the ones where the argument *is* the
content: the `O_NOFOLLOW` open in `dejima-project-lib.sh`, the id-derivation
anchoring in `dejima-audit`'s `ack`, `--check-origin` in `dejima-ttyd`.
Length is not the problem; length carrying no fact is.

Doing the pass is reading, not grepping. "used to" finds some of them and
also finds "deliberately not used to change how `$project` is resolved",
which means employed-to; and a comment can narrate what it replaced without
using the phrase at all. There is no test for this, which is why it is
written down here.

## Target `development`, not `main`

Branches here are opened against `development`, which merges to `main`
periodically. `main` stays releasable while work lands quickly; nothing else
about the workflow changes.

Moving `development` to `main` is not an ordinary merge, and is not something
to do as a follow-on to finishing a branch. It has its own pass - suites,
security review, documentation review, and the manual checks nothing here can
run - in [docs/release.md](docs/release.md), and `test/release-pass.sh` runs
what can be run and prints the rest. If you are asked to prepare a release,
start there rather than opening the pull request first. When the ask is to
run the pass, the pass is the whole of it: the report is the deliverable, the
release pull request is not part of it, and you never open one unasked.
Prompt the user to create it - the report is what they decide on.

`gitea-pr` prints the base it is opening against, every time, and reads
`git config gitea.prBase` before falling back to the repository's default
branch. On a checkout with that set, `gitea-pr create` targets the right
branch with no flag; on one without it, the line it prints is what tells you
otherwise. Pass `--base development` when you want to be sure.

Report the base it printed, not the one you meant. A pull request URL looks
identical whichever branch it is against, so nothing else will contradict a
wrong claim.

Rebase onto `origin/development` too, for the same reason: rebasing onto
`main` puts anything already merged to `development` back in your diff.
